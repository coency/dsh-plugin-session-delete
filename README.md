# dsh-plugin-session-delete

给 DeepSeek Harness (DSH) 补上官方不提供的删除会话能力：侧栏每个会话行的 `...` 菜单里多一个
「删除会话」，确认后把某个已存储会话连同它的注册表引用一起彻底清掉。

> DSH 本身只提供归档；清理已存储会话属于官方文档所说的"带外维护"（out-of-band maintenance）。
> 本插件把这件事自动化，并且顺序正确：先经官方写链摘除注册表引用，再删存储文件，
> 因此不会留下"内存把已删 id 写回文件"的脏数据。

## 它做什么

| 能力 | 入口 | 是否改数据 |
|---|---|---|
| 删除单个会话 | 侧栏 `...` → 「删除会话」 | 会，不可恢复 |
| 盘点还剩什么 | agent 调用 `session_delete_audit` | 只读 |
| 兼容性自检 | agent 调用 `session_delete_selfcheck` | 只读 |
| 清理无效标记 | 删除时 + 启动约 5 秒后自动 | 只动注册表标记 |

它刻意不提供：备份 / 回收站、批量勾选删除、定时自动清理。备份会让"删除"变成两处存储状态，
而不可预期的自动删除最容易变成事故。

## 安装

### 装之前

- 桌面端与 `dsh web` 都可以；Windows 上有真实宿主实测，Linux 目前只由 CI 跑测试覆盖（尚未在真实宿主上验证）。
- 插件依赖 DSH 的内部约定（不是公开的插件 API）。DSH 升级后可能需要跟着改几行，这是这套方案的成本。

### 桌面端（推荐）

「插件 → 添加插件」，填入：

```
github:coency/dsh-plugin-session-delete
```

需要固定版本时在地址后加 `#v0.3.1`。

装完通常即刻生效（桌面端会自动装载，必要时重启宿主子进程）。若侧栏的 `...` 里还没出现「删除会话」，
切换一下会话，或完全退出应用再打开。

### 网页端 / 命令行

```bash
dsh plugin --profile web add github:coency/dsh-plugin-session-delete
dsh web
```

profile 若为 `patchReload: live`，重启后即刻可用。

### 拿不到 GitHub 时（手动安装）

内网环境，或者只想装给自己：把仓库放进 profile 的 `vendor/`，再用 `file:` 依赖指过去。

1. 把整个仓库复制到 `~/.dsh/profiles/desktop/vendor/dsh-plugin-session-delete`
   （要含 `lib/`、`package.json`、`cordis.patch.yml`）。
2. 编辑同级的 `~/.dsh/profiles/desktop/package.json`：

   - 在 `dependencies` 里加一行
     `"dsh-plugin-session-delete": "file:./vendor/dsh-plugin-session-delete"`；
   - 在 `dsh.profile.bundles` 数组里加上 `"dsh-plugin-session-delete"`。

3. 完全退出应用，再打开。

以后升级就是覆盖 `lib/` 与 `package.json`，然后重启。

### 装完先自检

让 agent 跑一次 `session_delete_selfcheck`，看到这一行才算装对：

```
ok — every host contract this plugin uses is present — plugin 0.3.1 on dsh 0.2.2-rc.5 / node v24.21.0, markers "protocol", wire "accepted", 5 session(s) visible, 3/3 tool(s) registered.
```

版本号、三个工具的注册情况都在里面。对不上时，它还会写清楚是哪个契约变了。

## 使用

### 删一个会话

鼠标悬停侧栏任意会话行 → 点 `...` → 选「删除会话」→ 确认框会实时向宿主查询"将删除几个目录、
释放多少空间"，点「永久删除」才真正执行。不可恢复，也不保留备份。

### 先看还剩什么（只读）

不必先想好要删哪个 id。直接问 agent「还剩哪些会话没清掉」，它会调用 `session_delete_audit`，
把三处对不上的地方列出来：

- 有文件、但不在任何工作区成员列表里的会话；
- 有投影缓存记录、但会话文件已经不在的残留；
- 归档 / 置顶集合里指向"什么都没有"的标记（这类标记启动时也会自动清一次）。

它只读：不改文件、不改注册表。结果会带上这些条目占用的磁盘空间——列表被截断时标成"至少"。
注意"没被任何工作区列出"不等于真的没人管：工作区的会话列表本身是按索引过滤过的，所以这份报告
只当清理前的参考，不当"可以删"的证明。

### 交给 agent

三个工具：

| 工具 | 用途 | 参数 |
|---|---|---|
| `session_delete` | 删除一个已存储会话 | `sessionId`，可选 `dryRun`、`keepFiles` |
| `session_delete_audit` | 只读盘点 | 可选 `limit`（每次每类最多几条，默认 20） |
| `session_delete_selfcheck` | 只读兼容性自检 | 无 |

拿不准时先 `dryRun: true`，它只报告"会删什么、释放多少"，不动任何文件。

## 删除前请先看

> 前提：视图选项里的会话筛选要选 「全部对话（显示已归档）」，否则已归档的会话看不见，也就无从删除。

判据只有一个：宿主此刻有没有为这个会话运行中的 agent。

| 「永久删除」按钮 | 含义 | 怎么做 |
|---|---|---|
| 可点 | 宿主没有为它运行 agent | 直接点「永久删除」，删除后立刻从侧栏消失 |
| 置灰（禁用） | 宿主正占用它（里面有 agent 或后台任务在跑） | 先点「归档会话」停掉它的工作，再点「删除会话」——按钮恢复可用 |

在这个判据之外，还有几条规则要知道：

1. 与"用了多久""多久没用"无关：只看宿主此刻有没有为它运行 agent。
2. 归档 ≠ 释放内存：归档只是停掉它的工作，宿主仍把它记在内存里。所以已归档的会话能删，但删除后侧栏会留一条（在「全部对话（显示已归档）」里看得到）——那只是列表里的残留，不用管它；重启 DSH 后插件会在启动约 5 秒后把这条空标记清掉。
3. 重启 DSH 会让所有会话回到"没有 agent 在跑"的状态：如果有一批会话都删不掉，重启后再删最省事。
4. 分组不影响删除：工作区只是分组记录，删除工作区不会删除会话文件，那些会话会进入「未分组」；它们能否删除，仍按上表判断。
5. 删除不可恢复、不保留备份。

## 删除做了什么

1. 先动注册表（经 workspace domain 写链，内存与磁盘同时更新）：摘掉该会话在工作区成员、归档集合、
   置顶集合里的引用；
2. 再删文件：`$DSH_HOME/sessions/<project>/<id>/` 与会话投影缓存记录；项目目录空了顺手删掉；
3. 文件确认删除干净之后，才摘掉它的归档标记——中途失败时会话仍保持隐藏，不会以半删状态冒到侧栏里。

归档标记和置顶标记的清理分两处：删除时顺带复查，启动约 5 秒后再来一轮。每类每次最多做 32 次文件探测，
并且从上次停下的位置继续往下走（不会总卡在前几条），多出来的留给下一轮。启动那一轮是尽力而为，
失败只写 debug 日志。

## 已知限制

- 删除不可恢复，不做备份（刻意的：备份会让"删除"变成两处存储状态）。
- 未归档的活动会话删不掉：宿主仍持有它的写入句柄 → 先归档它（DSH 的归档动作会先停掉该会话的工作），然后再删——不需要重启 DSH。
- 已归档的会话可以直接删：即使它仍在宿主内存里（DSH 会把已归档会话保留到进程退出）。万一宿主退出时把内存里的内容补写了一次、目录又出现了，再删一次即可——那时它已不在内存中。
- 子代理会话的目录名是裸 UUID（不含 `session-` 前缀），本插件两种拼写都接受。
- 宿主插件不受工作区沙箱限制：它需要删除 `$DSH_HOME` 下的文件，代码很短、可审计。
- 同一会话不能并发删除：若同一会话已有一个删除在执行（比如你点了删除、agent 同时也在删它），第二个请求会立即返回"正在被删除"，等第一次结束后重试即可。这道串行化只在单个宿主进程内成立——桌面端与 `dsh web` 各跑一个宿主时，两边同时删同一个会话仍可能交错。
- 只清理会话自身的目录与投影缓存记录。`$DSH_HOME/attachments` 是内容寻址对象库、不按会话分目录，本插件不动它；若其中有只属于该会话的附件，会留下来。
- 启动清理以"文件是否还在"为判据：如果 `$DSH_HOME` 曾短暂半挂载（网络盘、移动盘），插件可能把暂时读不到的会话当成已删除、摘掉它的标记。有"至少一个存储根存在"这层护栏，风险很低；重连后建议跑一次只读审计确认。
- 投影缓存的历史整卷文件不处理：该会话的按记录缓存（`storages/session_projcache/sessions/<id>.json`）会被删除，但旧格式的整卷文件 `storages/session_projcache.json` 本插件不动。DSH 只在缺少按记录文件时才会从整卷文件重建记录，且会做身份校验，因此重建出来的旧记录不会再被采用。

## 兼容性

本插件依赖 DSH 的内部约定（不是公开的插件 API）。最近一次实测：

- 桌面端（宿主 dsh 0.2.2-rc.5、Node v24.21.0、Windows）：`session_delete_selfcheck` 返回 `verdict: ok`，
  `markers "protocol"`、`wire "accepted"`，三个工具全部注册；
- 更早的 dsh 0.1.7-rc.2（Web profile、Windows）与桌面端 0.2.0-rc.2 亦已通过。

0.3.0 新增了只读的 `session_delete_audit` 与一次启动清理，用到的宿主契约没有变化；0.3.1 修的是
"什么算一个会话目录"、注册表收尾失败的处理，以及置顶标记的清理。

插件加载后会自己跑一次轻量的启动自检（不读会话文件，只探两个存储根与注册表 API）。某个内部约定在
DSH 升级后移位时，宿主日志里会直接出现 `dsh-plugin-session-delete: startup check: …`，不必等到有人
怀疑功能坏了；菜单项消失或删除报错时，再跑一次 `session_delete_selfcheck` 拿完整报告。

刻意不声明任何 DSH peer 依赖：写死版本会让未来版本必须逐个走"版本豁免"，反而抬高安装门槛。

## 开发

### 结构

```
lib/index.js        宿主半边：工具注册、Remote 服务、启动探针与自检
lib/core.js         删除内核，宿主与浏览器两个面共用（顺序、路径校验、统计、审计）
lib/client.js       浏览器半边：侧栏菜单项与确认框
cordis.patch.yml    组合包补丁（一行宿主）
test/               零依赖测试
.github/workflows/test.yml   CI：Ubuntu / Windows × Node 22 / 24
```

### 测试

零依赖，只用 Node 自带的测试运行器（`engines: node >= 22.12`）：

```bash
npm test        # 等价于 node --test
```

覆盖会话 id 校验、`~` 展开、包含性判断、三态路径探测、字节统计（含 Windows junction 不被跟进）与
失败文案不含绝对路径，并在真实临时 `$DSH_HOME` 上跑删除端到端用例：删除顺序、`keepFiles`、
兄弟会话不被连带删掉、未知存储布局与"已加载未归档"的拒绝、并发删除串行化、部分失败时归档标记保留；
只读审计的分类（未归属会话、只剩缓存的记录、空标记）、标记清理的预算轮转，以及三个工具的注册与
拒绝路径都有独立用例。

CI 在 Ubuntu 与 Windows 上、Node 22 与 24 各跑一遍——Windows 那一份是专门盯着 junction 处理的。

> 在受限沙箱里 `node --test` 可能报 `spawn EPERM`（测试运行器要 spawn 子进程）。改用单进程模式即可：
> `node --test --experimental-test-isolation=none`。

## 卸载

桌面端：在「插件」页里卸载本插件，然后完全退出应用再重新打开。

网页端 / 命令行：

```bash
dsh plugin --profile web remove dsh-plugin-session-delete
```

手动安装的，删掉 `vendor/` 下的目录并移除 `package.json` 里的那一行，然后重启。

卸载后要重启一次 DSH，并刷新浏览器页面：

- 运行中的宿主进程可能仍持有已加载的插件模块——删掉文件、移除加载行都不足以让它卸载，只有重启进程才会
  真正卸下（这也是本插件安装后需要重启的同一个原因）；
- 浏览器里已经加载过的那份 bundle 同样要等页面刷新才会消失，否则侧栏可能还留着「删除会话」入口；
- 若 profile 是 `patchReload: live`，宿主侧通常会在卸载后即刻重组，但重启仍是最可靠的做法。

数据不会被恢复：已删除的会话就是删除了。
